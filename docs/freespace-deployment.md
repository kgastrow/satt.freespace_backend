# Freespace deployment guide

Audience: the person deploying the backend to a VPS and bringing a customer site live. Covers both supported topologies:

- **Host install**: systemd units, nginx or Apache on the same host (`app/backend/deploy/`, `app/backend/apache_site_config/`).
- **Docker compose**: `app/backend/docker-compose.prod.yml` (nginx, api, worker, PgBouncer, PostgreSQL, Redis).

Requirement IDs (BN-1, BF-35, ...) refer to `specs/BACKEND_FUNCTIONAL_DESCRIPTION.md`.

## 1. Prerequisites

- A VPS with a public IPv4 address and ports 80 and 443 reachable. Nothing else may be reachable from outside (see section 7).
- A **stable hostname** with a DNS A record to the VPS (for example `api.freespace.example.com`). Customer firewalls allow-list it by name, so changing it later means a change request at every customer (BN-1).
- PostgreSQL 15+, PgBouncer (transaction mode), Redis 7, Python 3.12 (host install) or Docker with the compose plugin.
- nginx 1.25.1 or newer (the vhost uses `http2 on;`) or Apache 2.4 with `proxy proxy_http proxy_wstunnel rewrite headers ssl setenvif`.
- certbot.
- A Firebase project with a service-account JSON for FCM (BF-68).
- An SMTP account for operator alerts (BF-82).
- Sizing reference (BN-3): 20 sites, 50 000 devices, one ingest per site every 30 s.

## 2. First deployment, step by step

### 2.1 Directories and secrets (once)

```bash
sudo install -d -m 0750 -o root -g www-data /etc/freespace /etc/freespace/fcm
sudo install -d -m 0750 -o www-data -g www-data /var/backups/freespace
# FCM service account (BF-68): outside the repository and any web root
sudo install -m 0640 -o root -g www-data service-account.json /etc/freespace/fcm/service-account.json
```

For compose, the host directory is `${FREESPACE_FCM_DIR:-/etc/freespace/fcm}`; the container user must be able to read the file (mode 0644 on a 0750 root-only directory is acceptable on a single-tenant VPS). The file is never committed, never copied into an image (`.dockerignore` excludes `service-account*.json`, `*credentials*.json`, `fcm/`) and never placed under a web root.

### 2.2 Configuration file

Create `config.json` **by hand** from `config.json.example` (host install) or `config.docker.json.example` (compose). Deployment does not copy it from the repository. Set at minimum: database credentials, `jwt.secret`, `encryption.key` (generate with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`), Redis URLs, SMTP, `public_url_frontend` / `public_url_backend` (docs/public-url-split.md), `server.debug: false`, and the Freespace keys in section 4. Mode 0640, owner `www-data` (host) or readable by the container.

Required for production:

```json
"server": { "debug": false, "trusted_client_ip_header": "X-Real-IP" },
"freespace": {
  "mock_mode": false,
  "mock_mode_acknowledged": false,
  "fcm_credentials_path": "/etc/freespace/fcm/service-account.json",
  "fcm_project_id": "<firebase project id>"
}
```

Compose uses `/run/freespace-fcm/service-account.json` for the path.

### 2.3 Database

Host install:

```bash
sudo -u postgres createuser --pwprompt appuser
sudo -u postgres createdb -O appuser appdb
```

Compose: set `DB_PASSWORD` (required), optionally `DB_USER`, `DB_NAME` in the environment or an `.env` file next to the compose file; the database is created on first start.

PgBouncer runs in transaction mode and the application connects through it (`database.pgbouncer_port`). Migrations and `pg_dump` connect to PostgreSQL directly.

### 2.4 Code, migrations, services

Host install:

```bash
cd app/backend && ./deploy/deploy.sh      # rsync, venv, pip, alembic upgrade head,
                                          # seed_maintenance, systemd units, restart
```

`deploy.sh` stops with an error if `/opt/freespace/backend/config.json` is missing. It never copies `config.json`, `.env` or `logs/` from the repository.

Compose:

```bash
cd app/backend
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml run --rm api alembic upgrade head
docker compose -f docker-compose.prod.yml up -d
```

Migrations are autogenerated (`make migrate-new`) and applied with `alembic upgrade head` only. Never hand-edit them; on a production database read each new file for `DROP`/type changes before applying (BN-4) and take a backup first.

### 2.5 The two seeders

| Script | When | What it does |
|---|---|---|
| `scripts/seed_first_tenant.py` | **Once**, on a fresh database | Reference data (roles, permissions including `sites:*`, `site_keys:write`, `site_push:*`, `site_events:read`, `site_alerts:receive`, the `operator` role, system config, rate limits, notification templates, cron definitions) plus identities (super admin, organizations, test users) and demo content. Set `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_FIRST_NAME`, `ADMIN_LAST_NAME` before running. **Delete or change the test users afterwards.** Never use `--force-clear` on a deployed database. |
| `scripts/seed_maintenance.py` | After **every deploy** that adds reference data (the host `deploy.sh` runs it) | Additive, re-runnable, touches no user, key or organization. `--list`, `--only`, `--skip role_permissions`, `--dry-run` are available. |

```bash
cd /opt/freespace/backend                     # or: docker compose ... run --rm api
ADMIN_EMAIL=ops@your-company.example ADMIN_PASSWORD='<strong>' \
  venv/bin/python scripts/seed_first_tenant.py
venv/bin/python scripts/seed_maintenance.py --list
```

The Freespace SystemConfig keys (section 5) are created by the shared seeder with the defaults shown there and are edited afterwards in the back office System Configuration screen.

### 2.6 First site, ingest key, app key

Sign in to the back office as the super admin.

1. Create the customer organization if needed (Organizations).
2. Sites: create the site (name, slug, time zone `Africa/Johannesburg` by default, FCM `topic`, capacity), then its zones. Leave **managed off** until section 9 says otherwise.
3. Site, ingest keys: create a key. The `fsk_...` value is **shown once**; give it to the ParkIT installer, who sends it as `Authorization: Bearer <key>`. Create a new key and revoke the old one as a separate action to rotate (BF-10b).
4. App keys (super admin only, `/api/v1/admin/app-keys`): create the key the mobile app sends in `X-Freespace-App-Key`. Shown once. It is deployment-wide.
5. Check connectivity from outside the VPS: `curl -H "Authorization: Bearer fsk_..." https://<host>/v1/ingest/ping` must answer 200 with the site name.

The same actions are available through the admin API under `/api/v1/admin/sites/...` and `/api/v1/admin/app-keys`.

### 2.7 FCM credential

Already placed in 2.1. Confirm with a **test push** (Site, Push, test push) to a development device. If the credential is wrong an operator alert is sent (BF-82). Rotating: replace the file, then restart `freespace-api` and `freespace-worker` (compose: `docker compose ... restart api worker`); the path is read at start.

### 2.8 Reverse proxy

nginx (host): copy `deploy/nginx.conf` to `/etc/nginx/sites-available/freespace`, replace `api.freespace.example.com` (all occurrences, including the certificate paths), symlink into `sites-enabled`, then `nginx -t && systemctl reload nginx`.

Apache: copy `apache_site_config/freespace.conf`, replace `freespace.example.com`, `a2enmod proxy proxy_http proxy_wstunnel rewrite headers ssl setenvif`, `apachectl configtest`, reload.

Compose: nginx is part of the stack; `deploy/nginx.conf` is mounted as a vhost and its upstream is rewritten to `api:8000` at container start. Do not mount it as `/etc/nginx/nginx.conf`.

What is proxied: `/v1/` (ingest and app), `/api/` (back office), `/health`. Not proxied (404): `/mock`, `/metrics`, `/docs`, `/redoc`, `/openapi.json`. The configs contain commented, labelled blocks for `/mock` (demonstration hosts only) and the API docs (development only).

**Client IP (BF-36).** The proxy overwrites `X-Real-IP` with the connecting address and discards client-supplied `X-Forwarded-For`, `Forwarded`, `CF-Connecting-IP` and `True-Client-IP`. The application must be told to trust exactly that header:

```json
"server": { "trusted_client_ip_header": "X-Real-IP" }
```

Per-IP rate limits (availability 60/min, sites 30/min, device 30/min per IP), the login lockout and audit rows all key on it. If left empty, every phone shares the proxy's address. `X-Forwarded-For` is refused at startup because proxies append to it. This is only sound while the proxy is the sole route to the API: the host unit binds `--host 127.0.0.1`, the compose api has no published port. If you later put a CDN in front, switch the header to the CDN's (`CF-Connecting-IP`) and change the proxy to pass it, and lock the origin to the CDN.

For the host install, `--forwarded-allow-ips='127.0.0.1'` stays as is. For compose it names the pinned subnet `172.28.0.0/16`.

### 2.9 TLS (BN-1)

```bash
sudo install -d /var/www/certbot
# Start the proxy on port 80 first (the 443 block fails until the certificate exists:
# comment it out for the very first run, or use `certbot certonly --standalone`
# before starting nginx).
sudo certbot certonly --webroot -w /var/www/certbot -d api.freespace.example.com
```

Renewal is automatic through the `certbot.timer` (or cron) that the package installs. Add a deploy hook so the proxy picks up renewed certificates:

```bash
# /etc/letsencrypt/renewal-hooks/deploy/reload-proxy.sh  (chmod +x)
systemctl reload nginx                                   # host install
# docker compose -f /opt/freespace/backend/docker-compose.prod.yml exec -T nginx nginx -s reload   # compose
```

Test with `sudo certbot renew --dry-run`. Port 80 serves only the HTTPS redirect and the ACME challenge. The firewall should allow 22 (restricted), 80 and 443 only.

### 2.10 Backups (BF-83)

`scripts/backup/freespace_backup.sh` (nightly `pg_dump`, custom format, checked with `pg_restore --list`) runs from `deploy/freespace-backup.service` / `.timer`. The script header lists every variable; the unit only supplies the environment file. The unit runs with `ProtectHome=true` (home directories are hidden) and `ProtectSystem=strict` (everything except the backup directory is read-only), so the SSH key, the pinned host key, `.pgpass` and any rclone config go in `/etc/freespace/` (mode 0600, owner www-data):

```bash
sudo install -m 0600 -o www-data -g www-data /dev/null /etc/freespace/pgpass   # 127.0.0.1:5432:appdb:appuser:<password>
sudo -u www-data ssh-keygen -t ed25519 -N '' -f /etc/freespace/backup_ed25519   # authorise the .pub on the target
ssh-keyscan offsite.example.com | sudo tee /etc/freespace/backup_known_hosts >/dev/null
sudo tee /etc/freespace/backup.env >/dev/null <<'EOF'
FREESPACE_BACKUP_DIR=/var/backups/freespace
FREESPACE_BACKUP_RETENTION_DAYS=14
FREESPACE_BACKUP_OFFSITE=backup@offsite.example.com:/srv/freespace/
FREESPACE_BACKUP_OFFSITE_METHOD=rsync
FREESPACE_BACKUP_SSH_KEY=/etc/freespace/backup_ed25519
FREESPACE_BACKUP_SSH_KNOWN_HOSTS=/etc/freespace/backup_known_hosts
# Optional second (or only) off-host copy:
# FREESPACE_BACKUP_RCLONE_REMOTE=remote:freespace
# RCLONE_CONFIG=/etc/freespace/rclone.conf
# Only on a host deliberately without an off-site copy:
# FREESPACE_BACKUP_ALLOW_LOCAL_ONLY=true
PGHOST=127.0.0.1
PGPORT=5432
PGUSER=appuser
PGDATABASE=appdb
PGPASSFILE=/etc/freespace/pgpass
EOF
sudo chmod 0600 /etc/freespace/backup.env
sudo systemctl enable --now freespace-backup.timer     # deploy.sh does this when the script exists
systemctl list-timers freespace-backup.timer
sudo systemctl start freespace-backup.service && journalctl -u freespace-backup -n 50
```

The timer runs 02:15 daily (`Persistent=true`, so a missed night runs at boot). Retention is 14 days locally; old local dumps are pruned only after the off-host copy succeeded. **An empty off-site destination fails the run**: set `FREESPACE_BACKUP_OFFSITE` and/or `FREESPACE_BACKUP_RCLONE_REMOTE`, or explicitly `FREESPACE_BACKUP_ALLOW_LOCAL_ONLY=true`. Host keys are checked strictly, so pin the target's key first. Use an rclone remote with static credentials (SFTP, S3 keys): `/etc` is read-only for the unit, so a remote that rewrites an OAuth token into its config fails. A backup that has never been restored is not a backup: do the restore drill below once before go-live.

With compose, run the same script on the host against a PostgreSQL reachable at the host (publish nothing; use `docker compose exec -T postgres pg_dump ...` inside a wrapper if the script supports it, or run the script in a one-off container on `freespace-network`).

## 3. Operating the services

| Task | Host install | Compose |
|---|---|---|
| Deploy a new version | `./deploy/deploy.sh` | `build`, `run --rm api alembic upgrade head`, `up -d` |
| Restart | `systemctl restart freespace-api freespace-worker` | `docker compose -f docker-compose.prod.yml restart api worker` |
| Logs | `journalctl -u freespace-api -f`, `-u freespace-worker -f` | `docker compose ... logs -f api worker` |

**Worker and engine tick (BF-50, BN-4).** One ARQ worker is enough. It runs the engine tick as a hard-coded cron at second 30 of every minute, the system cron scheduler every minute, and chunked fan-out (`max_jobs = 10`). All engine state (BF-5), in-flight advisories and send history are in PostgreSQL, so restarting the api and worker loses nothing. A tick that falls inside a restart gap is skipped and the next one proceeds. SIGTERM cancels jobs that are running; ARQ re-queues them and the fan-out is idempotent per device (BF-52, BT-02). Do not add a second worker unless the 5 000-device fan-out measurement says so.

Things in a redeploy that **would** violate BN-4 and are therefore avoided: copying `config.json` over the live one (fixed: excluded), a destructive migration (review before applying), `seed_first_tenant.py --force-clear` (never on a live database).

## 4. `config.json`: `freespace.*` and related keys

Read once at startup; a change needs a restart of api and worker.

| Key | Default | Meaning |
|---|---|---|
| `freespace.mock_mode` | `false` | Registers `/mock/*` and the simulator (BF-84). Off means those routes do not exist (404). |
| `freespace.mock_mode_acknowledged` | `false` | Second flag. With `server.debug` false and `mock_mode` true, the application refuses to start unless this is also true. |
| `freespace.fcm_credentials_path` | `""` | Absolute path to the FCM service-account JSON, outside the repository and web roots (BF-68). Empty disables push delivery. |
| `freespace.fcm_project_id` | `""` | Firebase project id. |
| `rate_limit.freespace_availability` | `60/minute` | Per IP, `GET /v1/sites/{slug}/availability` (BF-36). |
| `rate_limit.freespace_sites` | `30/minute` | Per IP, `GET /v1/sites`. |
| `rate_limit.freespace_device_per_id` | `10/minute` | Device `PUT`/`DELETE` per deviceId (hashed). |
| `rate_limit.freespace_device_per_ip` | `30/minute` | Device `PUT`/`DELETE` per IP. |
| `rate_limit.freespace_ingest` | `12/minute` | Ingest per ingest key (BF-18); 429 carries `Retry-After`. |
| `server.trusted_client_ip_header` | `""` (`X-Real-IP` in the docker example) | The one header the proxy overwrites with the client address. Required behind a proxy. |
| `server.debug` | `true` in the example | **Must be `false`** in production; it also disables the mock-mode guard and the client-IP startup check. |

## 5. SystemConfig keys (back office, System Configuration; 60 s cache)

| Key | Default | Meaning |
|---|---|---|
| `freespace.limit_scope` | `DEVICE` | `DEVICE`: cooldown and daily cap apply across all sites a phone follows. `DEVICE_PER_SITE`: each site's own settings (BF-63). |
| `freespace.cooldown_s` | `1800` | Seconds between advisories to one phone (DEVICE scope). |
| `freespace.daily_cap` | `2` | Maximum advisories per phone per day (DEVICE scope). |
| `freespace.time_zone` | `Africa/Johannesburg` | Defines "today" for the daily cap. |
| `freespace.device_ceiling` | `50000` | Registered-device ceiling; beyond it registration answers 503 and an operator alert fires (BF-37). |
| `freespace.retention.devices_days` | `90` | Devices not updated for this long are erased (BF-73). |
| `freespace.retention.send_history_days` | `35` | Send history retention. |
| `freespace.retention.events_days` | `365` | Event log retention. |
| `freespace.retention.occupancy_history_days` | `180` | Occupancy history retention. |
| `request_logs.retention_days` | `30` | Back-office request-log retention (template key, reused). |

Per-site settings (thresholds, hold time, notification window, `managed`, `listed`, templates) are edited per site in the back office, not here.

## 6. Mock mode for a demonstration, and the production guard

Mock mode lets a demo host fabricate occupancy (`POST /mock/sites/{slug}/occupancy`), advance an injected clock (`POST /mock/clock`) and show the simulator for the acceptance scenarios AT-01 to AT-08. It must never run in production.

To enable on a **demo host only**:

1. `config.json`: `"freespace": {"mock_mode": true, "mock_mode_acknowledged": true, ...}` (or `server.debug: true` on a laptop, which needs no acknowledgement).
2. Proxy: remove the `/mock` rewrite rule (Apache) or uncomment the labelled `location /mock/` block (nginx).
3. Restart api and worker.

Guard: with `mock_mode: true`, `server.debug: false` and `mock_mode_acknowledged: false` the application raises at import time (`create_application`) and does not start, before any route is built. With `mock_mode: false` (default) `/mock/*` returns 404, and in production the proxy does not forward `/mock` at all, so it is 404 there regardless of the application. After deploying, verify: `curl -i https://<host>/mock/clock -X POST` returns 404.

## 7. Network exposure (BN-1)

Only 443 (plus 80 for the redirect and certificate challenge) is public.

- Compose: `docker-compose.prod.yml` publishes only nginx `80` and `443`. PostgreSQL, PgBouncer, Redis, api and worker have no `ports:` and live on the private `freespace-network` (`172.28.0.0/16`, pinned so `--forwarded-allow-ips` can name it). The development `docker-compose.yml` publishes its ports on `127.0.0.1` only.
- Host install: the API binds `127.0.0.1:8000`; keep PostgreSQL (5432), PgBouncer (6432) and Redis (6379) bound to localhost or a private interface and block them in the firewall (`ufw default deny incoming; ufw allow 22,80,443/tcp`).
- Redis has no password in the shipped examples: that is acceptable only because it is not reachable from outside the host or compose network.

## 8. Health check, logs, restore

### Health check

Uptime monitor: `GET https://<host>/health`, expect HTTP 200 `{"status":"healthy", ...}`. It is unauthenticated and returns status only (BF-80): 503 when the database does not answer or the worker's engine tick is older than three minutes (`engine.status` `stale`; `no_tick_yet` in the first five minutes after an API start). Alert on non-200 or no answer within 10 s, checked every minute.

Liveness: `GET http://127.0.0.1:8000/health/live` answers 200 whenever the API process is up and checks nothing. The Dockerfile `HEALTHCHECK`, the compose healthchecks and `deploy/deploy.sh` use it, so a stalled worker (which turns `/health` red) never restarts the API. Never point a restart policy at `/health`. `/health/detailed` (database, Redis, queue) is not proxied; run it from the host: `curl -s http://127.0.0.1:8000/health/detailed`.

### Log locations and what they do not contain

| Log | Location | Notes |
|---|---|---|
| Proxy access (nginx) | `/var/log/nginx/freespace-api-access.log` (compose: `app/backend/logs/nginx/`) | Masked format: address, time, method, path, status, bytes, timings, user agent. |
| Proxy access (Apache) | `${APACHE_LOG_DIR}/freespace-access.log` | Same content. |
| Proxy error | `freespace-api-error.log` / `freespace-error.log` | Device paths are suppressed (see below). |
| Application | `app.log` and `request_response.log` in the working directory (`/opt/freespace/backend/` or `/app` in the container; compose `./logs`), plus journal / container stdout | Request log stores the matched route template, not the raw path (D5). |

**uvicorn's own access log is switched off** (`--no-access-log` in `deploy/freespace-api.service`, `docker-compose.prod.yml` and the `Dockerfile` CMD). It prints the raw request line, which would put `/v1/devices/<deviceId>` (a bearer secret, BF-35) into the journal or container stdout. Request logging is done by the application's own middleware (route templates only) and the proxy's masked access log above. Do not remove the flag, and add it to any other way of starting the API (a custom `uvicorn` or `gunicorn` command). SQLAlchemy engines run with `hide_parameters=True`, so statement parameters (FCM tokens) never appear in database error text either.

What the proxy logs **do not** contain (BF-35): the deviceId (the path `/v1/devices/<deviceId>` is written as `/v1/devices/:id`, including `%`-encoded and double-slash spellings), the query string, the `Authorization` header (ingest keys), the `X-Freespace-App-Key` header, cookies, the Referer, request or response bodies, FCM tokens. Client IP addresses **are** logged; they fall under the BF-73 retention policy, so rotate and delete proxy logs after 30 days:

```
# /etc/logrotate.d/freespace-proxy
/var/log/nginx/freespace-*.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    sharedscripts
    postrotate
        [ -f /run/nginx.pid ] && kill -USR1 $(cat /run/nginx.pid)
    endscript
}
```

Verify the masking after any proxy change:

```bash
curl -s -o /dev/null -X PUT https://<host>/v1/devices/TESTDEVICE123456 -H 'Content-Type: application/json' -d '{}'
curl -s -o /dev/null "https://<host>/v1/%64evices/TESTDEVICE123456"
grep -rc TESTDEVICE123456 /var/log/nginx/ /opt/freespace/backend/*.log     # every count must be 0
```

Residual risk: a request rejected before the proxy picks a location (a malformed request line) is recorded by the server-level error log; use `error_log ... crit;` there if a hard guarantee is required.

### Restore from backup (outline)

1. Stop writers: `systemctl stop freespace-api freespace-worker` (compose: `stop api worker`).
2. Create an empty database (or a scratch one for a drill): `createdb -O appuser appdb_restore`.
3. Restore the newest dump: `pg_restore --no-owner --role=appuser -d appdb_restore /var/backups/freespace/<file>.dump` (or `psql -f` for a plain-SQL dump, whichever the backup script writes).
4. Point `config.json` at it (or rename databases), run `alembic upgrade head` (the code may be newer than the dump), then `scripts/seed_maintenance.py`.
5. Start worker, then api. Engine state (BF-5) comes back with the data; the first tick after start re-evaluates every site. Watch `/health` and the event log. Devices keep their registrations (hashed ids), so phones need not re-register; advisories sent after the dump but before the loss may be repeated once.
6. Record the drill date and how long it took.

## 9. Go-live checklist for a new site (shadow mode, BF-61, spec 15.1)

Pre-flight (once per VPS): HTTPS valid on the stable hostname and `certbot renew --dry-run` passes; `/health` monitored; `mock_mode` off and `/mock/clock` is 404; `server.debug` false; `trusted_client_ip_header` set and two requests from different IPs show different addresses in the proxy log; the device-id log check in section 8 passes; backup timer active and a restore drill done; FCM test push received; operator alert recipients hold `site_alerts:receive`.

Per site:

1. Create the site with **`managed = false`**, correct time zone, capacity, `topic` (an existing site such as ABSA keeps `ABSA-270RR` and its legacy notifier until the cut-over), zones and message templates; leave `listed` off until data is flowing.
2. Create an ingest key and give it to the ParkIT installer. Check `GET /v1/ingest/ping` shows the right site name and a small clock skew.
3. Let ParkIT publish. Confirm the snapshot updates every 30 s, health is not `STALE`, and no `INGEST_REJECTED` events appear.
4. Shadow mode: the engine evaluates every minute and logs each candidate as `UNMANAGED`; nothing is sent. Review the event log for several days of real occupancy and tune thresholds, hold time, window and zone priorities until the candidates are what the site should receive.
5. Check the mobile app against the site (`listed` on): availability, recommended zone, stale handling.
6. Cut-over in **one change window**: switch the legacy notifier off in ParkIT, then set `managed = true`. Never have both on or phones receive two pushes.
7. Watch the first live advisory: send history, cooldown and daily cap behaviour, FCM errors, operator alerts. Keep the previous ingest key until the new publisher is confirmed, then revoke it.
8. Announce the hostname, ingest key and contact to the customer; record the key's name and expiry.
