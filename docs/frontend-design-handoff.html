01Stack

Everything is client-rendered from a Vite bundle against a FastAPI backend. There is no SSR, no CSS-in-JS, and no separate design-system package — components live in the app repo and are edited directly.

02Navigation zones

The app is split into five addressable areas with different audiences and different chrome. Three of them (app, admin hub, platform admin) are formal permission-gated navigation zones in the codebase; the split is enforced there, so it is the structure any new design has to work with. Colour coding below is used throughout this document only.

ZoneAudienceChrome
PublicAnonymous visitorsCentred card on a plain ground, no sidebar
AppEvery signed-in userCollapsible left sidebar + header, mobile drawer
SettingsEvery signed-in userSecondary settings nav nested inside the app shell
Admin hubOrganisation administratorsOwn sidebar with collapsible categories, at /admin
Platform adminCross-tenant super adminsOwn sidebar, at /platform-admin

The rule that governs placement

Requiring a permission does not make a page an admin page. Day-to-day work for the product's primary users belongs in the app sidebar; infrequent configuration and reference-data management belongs in the admin hub. Features often span both — an end-user view in the sidebar and its configuration screen in the admin hub.

Typography

No custom typeface is loaded today — the app runs on the system UI stack. Choosing and specifying a face (and its fallback stack, weights and scale) is open work. Long-form article content is styled by the Tailwind typography plugin, so a prose scale is needed as well as a UI scale.

06Cross-cutting UI

Behaviours that appear on many screens at once. Each one needs a designed state, and several of them stack vertically above the page content.

  • Banner stack. Up to five banners can appear above the app content simultaneously: announcement, impersonation, pending account deletion, PWA install prompt and new-version-available. They need a defined stacking order, a compact height, and dismiss behaviour.
  • Permission gating. Any nav item, page or individual control can be hidden or replaced based on the signed-in user's permissions. Designs should say, per control, whether an unpermitted user sees nothing or sees a disabled state.
  • Loading. Skeletons for cards, forms and tables; a full-page loader for route transitions. Data comes from a cache, so screens can also render stale content while refreshing.
  • Empty and error states. Every list and table needs one of each. There is a route-level error boundary and an in-page fallback component.
  • Real time. Notifications, announcements, maintenance mode and data-export progress arrive over WebSocket and change the UI without a reload — including a full-screen takeover when maintenance mode is switched on.
  • Impersonation. Admins can act as another user. While impersonating, a persistent banner and indicator are shown and must be unmistakable.
  • Onboarding. A configurable multi-step wizard with progress, admin-defined fields and an admin review queue. Field types and step count are data, not code — the design has to survive an arbitrary number of steps.
  • Two-factor. QR-code enrolment, OTP entry, recovery codes, and an organisation-wide enforcement mode that blocks the app until 2FA is set up.
  • Responsive. Mobile-first Tailwind breakpoints. On small screens the sidebar becomes a drawer; tables are the main pressure point and currently rely on horizontal scroll.
  • Accessibility. Radix supplies roles, focus management and keyboard interaction. Playwright tests select elements by accessible name, so visible labels are load-bearing — icon-only controls need accessible names.

07Constraints

Things that will cause rework if the design ignores them.

  1. Design to tokens, not to hex values. Anything specified as a one-off colour breaks dark mode, because dark mode works entirely by re-declaring the token set.
  2. Both themes are shipped. Every screen, banner, chart and illustration needs a light and a dark treatment. Dark is not an afterthought toggle.
  3. Every string is translated. Labels must tolerate roughly 30–40% expansion. Avoid layouts that depend on a specific word length, and avoid text baked into images.
  4. Stay inside the primitive set where possible. A new variant of an existing shadcn component is cheap; a bespoke interactive control is expensive and loses the Radix accessibility behaviour.
  5. Navigation zones are structural. Placing a page in the wrong zone is a code change, not a visual one. Decide zone before layout.
  6. Long lists are virtualised. Rows need a consistent height; variable-height cards in a long scroller are a problem.
  7. The template's main sidebar is nearly empty by design. The product's own IA is the thing being added — don't design around Dashboard alone.

08Gaps to design

Open work, in rough priority order.

  • Brand identity. The palette is intentionally neutral greyscale and there is no logo, no typeface and no illustration style. All of it is unspecified.
  • Typography system. No web font is loaded; UI and prose scales both need defining.
  • Data visualisation. Five chart tokens exist but no charting library is wired up. The Metrics and Reports screens are currently cards and badges. Chart style and library choice are open.
  • The product's own screens. Everything in the app sidebar beyond Dashboard, Files, Notifications and Profile is new work.
  • Dashboard. Shipped as a placeholder. Its composition is the most visible single design decision.
  • Empty states. Present but generic; no illustration or voice.
  • Mobile tables. Currently horizontal scroll. A card-per-row pattern is likely wanted.
  • Marketing surfaces. The landing page is a stub; login and register are plain centred cards.
