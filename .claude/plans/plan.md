# Reports & Data Export - Multi-Phase Implementation Plan

**Issue:** #34 - [Greenfield] Reports & Data Export
**Branch:** `feat-issue-34-adw-20260212030055-0ec23842357f-reports-data-export`
**Date:** 2026-02-14

## Overview

This plan implements report generation for Vehicle Activity, Device Performance, Volume, Watchlist Hit, and Violation reports. It also implements a Storage Usage page showing consumption by data type. The existing report infrastructure (models, CRUD, API, frontend page, scheduling) is already in place — this plan adds the **missing report generators**, **scheduled report execution**, **multi-format export (PDF/CSV/Excel)**, and the **Storage Usage page**.

## What Already Exists

- **Models:** `Report`, `ReportSchedule` — fully defined with status tracking, file storage link, scheduling
- **CRUD:** `report.py`, `report_schedule.py` — list/create/update/delete/get + `get_due_report_schedules()`
- **API:** `report.py` (5 endpoints), `report_schedule.py` (5 endpoints) — registered in v1 router
- **Service:** `ReportService` with `generate_report()` orchestration, registry pattern for generators
- **Generators:** Only `users_report` currently registered (CSV only)
- **Cron:** `process_scheduled_reports_handler` exists as placeholder
- **Frontend:** `ReportsPage.tsx` with tabs (reports/schedules), `reportsApi.ts` RTK Query endpoints
- **i18n:** Full translations in `admin.json` for reports UI
- **Permissions:** `reports:read`, `reports:write`, `reports:delete`, `reports:schedule`
- **Dependencies:** ANPR Events, Devices, Device Health, Watchlists/Alerts, Redlight Violations — all have models and CRUD functions

## What Needs To Be Built

1. **5 new report generators** (vehicle_activity, device_performance, volume, watchlist_hit, violation)
2. **Multi-format export** (PDF, CSV, Excel) — extend `ReportService` to support `export_format` parameter
3. **Scheduled report execution** — implement the placeholder cron handler + email delivery
4. **Storage Usage backend** — CRUD and API for per-org storage consumption by data type
5. **Storage Usage frontend** — Page with visual threshold indicators
6. **Frontend enhancements** — Export format selection in report create dialog, report type parameter forms
7. **Backend tests** — CRUD, API, tenant isolation, report generators
8. **Frontend tests** — Component tests for new UI

### Phase 1A: Multi-Format Export Infrastructure

**Files to modify:**

- `app/backend/src/services/reports/__init__.py` — Update `ReportGenerator` type to return structured data

- `app/backend/src/services/reports/users_report.py` — Refactor to new generator signature
- `alembic/` — Migration for `export_format` column (autogenerated via `make migrate-new`)

**Implementation details:**

1. **Add `export_format` column** to `Report` model:
   ```python
   export_format: Mapped[str] = mapped_column(String(10), nullable=False, default="csv")
   ```
   Valid values: `"csv"`, `"excel"`, `"pdf"`

2. **Create `export_formats.py`** with format converters:
   - `format_csv(headers: list[str], rows: list[list[Any]]) -> tuple[bytes, str]` — Returns (bytes, "text/csv")
   - `format_excel(headers: list[str], rows: list[list[Any]], sheet_name: str) -> tuple[bytes, str]` — Returns (bytes, "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet")
   - `format_pdf(headers: list[str], rows: list[list[Any]], title: str, metadata: dict) -> tuple[bytes, str]` — Returns (bytes, "application/pdf")
   - PDF metadata includes: organization name, date range, generation timestamp (from acceptance criteria)
   - Dependencies: `openpyxl` for Excel, `reportlab` for PDF

3. **Update `ReportGenerator` signature** — Generators return `tuple[list[str], list[list[Any]], dict]` (headers, rows, metadata) instead of `(bytes, content_type, row_count)`. The service applies the format converter afterward. This cleanly separates data generation from formatting.

4. **Update `ReportService.generate_report()`** to:
   - Accept `export_format` parameter (default: "csv")
   - Call generator → get (headers, rows, metadata)
   - Apply format converter → get (bytes, content_type)
   - Set correct file extension (.csv/.xlsx/.pdf) in filename
   - Store `export_format` on Report record

5. **Update serializers** — Add `export_format` field to `ReportCreateRequest` (optional, default "csv", validated against allowed values) and `ReportResponse`

6. **Autogenerate migration** — `make migrate-new msg="add_report_export_format"`

7. **Refactor `users_report.py`** — Update to return (headers, rows, metadata) instead of (bytes, content_type, row_count)

### Phase 1B: Report Generators

**New files:**
- `app/backend/src/services/reports/vehicle_activity_report.py`
- `app/backend/src/services/reports/device_performance_report.py`
- `app/backend/src/services/reports/volume_report.py`
- `app/backend/src/services/reports/watchlist_hit_report.py`
- `app/backend/src/services/reports/violation_report.py`

**File to modify:**
- `app/backend/src/services/reports/__init__.py` — Register all 5 new generators in `_register_all_generators()`

**Report specifications:**

1. **Vehicle Activity Report** (`vehicle_activity_report`)
   - Data source: `AnprEvent` + `Event` + `DeviceChannel` + `Device`
   - Columns: Event Time, VLN, Confidence, Region, Vehicle Class, Direction, Device, Channel, Watchlist Match
   - Parameters: `date_from`, `date_to`, `device_id`, `vln`, `vehicle_class`
   - Follows existing `stream_anpr_events_csv()` pattern from `crud/anpr_event.py` for batched streaming
   - Joins: Event → AnprEvent → DeviceChannel → Device, left outer join to Alert for watchlist match

2. **Device Performance Report** (`device_performance_report`)
   - Data source: `Device` + `DeviceHeartbeat` + `DeviceChannel`
   - Columns: Device Name, MAC Address, Status, Channel Count, Avg CPU Temp, Uptime %, Error Count, Last Heartbeat
   - Parameters: `date_from`, `date_to`, `device_id`, `status`
   - Aggregates heartbeat data per device for the period using `get_fleet_health_summary()` pattern
   - Calculates uptime as % of expected heartbeats vs received in period

3. **Volume Report** (`volume_report`)
   - Data source: `Event` (aggregated counts)
   - Columns: Date, Hour (if hourly), Device, Channel, Total Events, ANPR Events, Redlight Events
   - Parameters: `date_from`, `date_to`, `device_id`, `granularity` ("hourly"/"daily", default "daily")
   - Uses `func.date_trunc()` for time bucketing, GROUP BY device + channel + time bucket

4. **Watchlist Hit Report** (`watchlist_hit_report`)
   - Data source: `Alert` + `WatchlistEntry` + `Watchlist` + `AnprEvent` + `Event`
   - Columns: Alert Time, VLN, Watchlist Name, Entry Reason, Priority, Acknowledged, Acknowledged By, Notes, Device, Channel
   - Parameters: `date_from`, `date_to`, `watchlist_id`, `priority`, `acknowledged`
   - Uses existing `get_alerts()` CRUD pattern with eager loading

5. **Violation Report** (`violation_report`)
   - Data source: `RedlightEvent` + `Event` + `DeviceChannel` + `Device`
   - Columns: Event Time, VLN, Confidence, Vehicle Class, Direction, Review Status, Dismissal Reason, Reviewed By, Device, Channel
   - Parameters: `date_from`, `date_to`, `device_id`, `review_status`, `vln`
   - Follows existing `stream_redlight_violations_csv()` pattern from `crud/redlight_event.py`

**All generators follow the same pattern:**
- Signature: `async def generate_X_report(session, organization_id, parameters) -> tuple[list[str], list[list[Any]], dict]`
- Use batched streaming (BATCH_SIZE=500) — collect into rows list for format-agnostic output
- Include metadata dict with: `org_name`, `date_range`, `generated_at`, `report_title` (used in PDF header)
- Filter by `organization_id` and `deleted_time.is_(None)` in all queries

## Phase 2: Scheduled Report Execution + Email Delivery

**Goal:** Implement the scheduled report cron handler to generate reports and email them to recipients.

### Phase 2A: Cron Handler Implementation

**Files to modify:**
- `app/backend/src/services/cron/reports.py` — Implement `process_scheduled_reports_handler` (replace placeholder)

**Implementation:**
1. Query due schedules using existing `get_due_report_schedules(session)` from CRUD
2. For each due schedule:
   a. Call `report_service.generate_report()` with schedule's `report_type`, `parameters`, `schedule_id`, default `export_format="csv"`
   b. If report completed successfully AND schedule has recipients:
      - Enqueue `send_report_email_task` via `task_queue.enqueue_job()`
   c. Update schedule via `update_schedule_run_status()` — set last_run_time, last_run_status, recalculate next_run_time
3. Handle errors per-schedule (don't let one failure block others) — catch Exception, log, update schedule with error status
4. Return `{"status": "completed", "reports_processed": count, "errors": error_count}`

### Phase 2B: Email Delivery Task for Scheduled Reports

**Files to modify:**
- `app/backend/src/workers/tasks.py` — Add `send_report_email_task`
- `app/backend/src/workers/worker.py` — Register task in `functions` list with `instrument_task`

**Implementation:**
- Task signature: `send_report_email_task(ctx, report_id: str, recipients: list[str], organization_id: str)`
- Steps:
  1. Get report from DB using `get_report_by_id()`
  2. Get download URL for report file using file manager
  3. Send email to each recipient using `notification_dispatcher.send_to_user()` or direct `email_service.send_email()` with report name, download link, and generation timestamp
  4. Use template-based email with report name and download link
- Set `_job_timeout = 120` (2 minutes per email batch)
- Retry on transient failures with `Retry(defer=60)`

### Phase 2C: Tests for Scheduling

**New files:**
- `app/backend/tests/service_tests/test_report_scheduling.py`

**Tests:**

## Phase 3: Storage Usage Backend

**Goal:** API for viewing storage consumption by data type with threshold indicators and notifications.

### Phase 3A: Storage Usage CRUD + Serializers + API

**New files:**
- `app/backend/src/crud/storage_usage.py` — Aggregate storage queries
- `app/backend/src/serialisers/storage_usage.py` — Response models
- `app/backend/src/api/storage_usage.py` — API endpoint

**Files to modify:**
- `app/backend/src/api/v1/__init__.py` — Register `storage_usage.router` (before file.router — more specific route first)
- `app/backend/src/core/response_codes.py` — Add storage response codes if needed

**CRUD: `get_organization_storage_usage(session, organization_id)`**
- Query `File` model grouped by `category` — returns: category, SUM(size_bytes), COUNT(*)
- Filter: `organization_id`, `deleted_time.is_(None)`, `status='ready'`
- Also query total `Event` count and `DeviceHeartbeat` count for the org (data volume indicators)
- Query `OrganizationFileSettings` for `org_storage_quota_bytes`, `user_storage_quota_bytes`
- Calculate threshold status: `green` (<80%), `warning` (80-95%), `critical` (>95%)

**Serializers:**
```python
class StorageCategoryUsage(BaseModel):
    category: str  # "image", "video", "document", "audio", "other"
    total_bytes: int
    file_count: int
    percentage: float  # of total

class DataVolumeInfo(BaseModel):
    event_count: int
    heartbeat_count: int

class StorageUsageResponse(BaseModel):
    categories: list[StorageCategoryUsage]
    total_bytes: int
    total_files: int
    quota_bytes: int | None  # None = unlimited
    usage_percentage: float | None  # None if no quota
    threshold_status: str  # "green", "warning", "critical"
    data_volume: DataVolumeInfo
```

**API endpoint:**
- `GET /storage-usage` — permission: `reports:read`
- Returns `StorageUsageResponse`
- Router prefix: `/storage-usage`, tags: `["storage-usage"]`

### Phase 3B: Storage Threshold Notifications

**Files to modify:**
- `app/backend/src/services/cron/storage.py` — Add threshold check logic

**Implementation:**
- After existing storage recalculation, check usage vs quota
- If warning threshold (80%) newly exceeded → send in-app notification via `notification_dispatcher.send_in_app_notification()`
- If critical threshold (95%) newly exceeded → send email + in-app notification
- Track last notification time in `SystemConfig` to avoid spam (e.g., `storage_warning_last_notified_{org_id}`)
- Only notify org admins (users with `reports:read` permission or org owner/admin role)
